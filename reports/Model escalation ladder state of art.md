# Escalation ladders: sound core, costly handoffs

**Verdict (as of October 2026).** The ladder's core is well aligned with the literature. Cheap-first operation, escalation on grounded behavioural signals (loops, repeated errors, truncation, refusal, failed review), a three-strike breaker, bounded review rounds and a consult tool alongside full switching all match what shipped systems and recent papers converge on. Four things look overlooked or under-specified. First, escalation hands the stronger model the full cheap-model trajectory, and 2026 work on coding agents finds this recovers less than half the quality gap ([The Handoff Tax](https://arxiv.org/abs/2608.24358)). Second, every rung change is a cold cache, and the 143K and 169K re-writes you measured are the expected cost, not an anomaly ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Third, the detectors are purely syntactic, so they miss the stalls that are most common in coding agents (long read-only exploration, edit/revert oscillation, test-fix thrash). Fourth, the reviewer's evidence design, not its size, decides its accuracy. Anthropic's own advice is to benchmark a stronger model at low effort against any cheap-first scheme, and the ladder has not yet done that. Almost all 2026 agent-routing evidence is abstract-level or self-reported (see the evidence-quality section). Treat the recommendations as well-motivated hypotheses to test live, not proven fixes.

## Scorecard: each design decision against prior work

"Confirmed" means the direction is supported. It does not mean the parameters are validated, because almost nobody publishes tuned thresholds.

## Cache and handoff costs dominate the economics of switching

Your live measurements agree with the vendor documentation. Anthropic states that each model has its own cache, so a model switch makes the next request read the whole history with no cache hits ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Cache writes cost **1.25x** base input and reads cost **0.1x**, with a lower read multiplier on some newer models ([Anthropic caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). The first request after a switch is therefore roughly an order of magnitude dearer than the same request on a warm cache, on top of the price delta between models. At 143K to 169K tokens, one escalation is a non-trivial bill, and a later step-down pays it again unless the old model's cache is still alive (5-minute TTL by default outside a subscription's main conversation). Claude Code itself skips its switch warning once the cache has expired, which is the same logic: switch when the cache is already cold or the context is small.

Cost is not the only price. The Handoff Tax study of coding agents reports that escalating from a low-cost to a high-cost model with the full trajectory "recovers less than half" of the quality gap at a substantial cost premium, that trimming inherited trajectory information improves quality, and that the best context interface reverses with direction ([arXiv 2608.24358](https://arxiv.org/abs/2608.24358)). This is abstract-level evidence, but it targets exactly your scenario. A cheap model that was looping leaves a history full of wrong turns, and the stronger model may imitate them. A companion result is that swapping models mid-trajectory changes behaviour sharply, with 74-77% of early swaps diverging at the very first action after the switch ([Replay Gap](https://arxiv.org/abs/2608.08239)). Escalation is real intervention, not a transparent upgrade.

A practitioner report adds a cost warning in the other direction: a cheaper model that loops can cost more in total than a stronger model that finishes in one pass ([Sonar blog](https://www.sonarsource.com/blog/we-switched-to-a-5x-cheaper-llm-our-costs-went-up/), non-primary). Anthropic's advisor data points the same way. A strong executor with the strongest advisor gained 1.7 points for about 2.1x the cost, and the benefit shrinks as the executor approaches the advisor's capability ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence), vendor, via summarising fetch). A ladder spanning Haiku to Opus has real gaps to exploit at the bottom, and little to gain between the top rungs.

## Detectors catch repeats but miss the stalls that dominate coding failures

The ladder's loop signals are the right hard triggers, and the three-strike threshold matches what Aider, Roo and OpenHands ship. What the published failure analyses add is that exact repetition is the minority case. In multi-agent traces, step repetition accounts for **15.7%** of annotated failures, and that figure comes from a search-engine summary of the MAST paper rather than the PDF ([MAST](https://arxiv.org/pdf/2503.13657)). In SWE-bench trajectories, the structural anti-patterns are different: a "search loop" of 10 or more consecutive read-only actions appears in **56.1% of failed runs versus 41.1% of resolved runs**, with re-read churn at 44.7% versus 34.0%, plus edit/revert oscillation and phase oscillation ([TraceProbe](https://arxiv.org/html/2607.06184v1)). Failed runs are also 12-57% longer across three agents ([2511.00197](https://arxiv.org/html/2511.00197v1)). Because the same patterns occur in many successful runs, they discriminate weakly and belong in the escalation score, not in an abort path.

Three breaker details matter. First, state: Claude's SDK keeps budget totals in the session transcript and deliberately does not apply caps to restored totals, and budgets restart on `/clear`. A breaker whose state lives in a hot-reloadable module resets on reload. Second, the failure pattern in other tools' bug trackers: warn once and never re-detect, warnings masking hard stops, detection off by default, and counters that reset on trip ([oh-my-pi #12564](https://github.com/can1357/oh-my-pi/issues/12564), [deer-flow #5243](https://github.com/bytedance/deer-flow/issues/5243); user reports). Third, half-open: commentators call it the hardest state to translate to stochastic agents because one success does not prove recovered reasoning quality ([Hannecke](https://medium.com/@michael.hannecke/resilience-circuit-breakers-for-agentic-ai-cc7075101486), snippet only). Your "deny tools until the next prompt" is a reasonable open state with the human as the probe, which is also what Roo does. The risk is the Cline lockout: a cap with no way to continue.

## Model-called signals and the oracle under-fire exactly when they are most needed

Anthropic reports that without prompt steering the executor under-calls the advisor "particularly" on coding tasks, that a tuned prompt block lifted Haiku by about 7.5 points on an internal coding benchmark, and that low-effort executors can stop detecting that they are stuck ([advisor docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool); [Optimizing page](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence); vendor-reported). Your `request_escalation` and `consult_oracle` share this weakness, and the verbalized-confidence literature says the stated number skews high ([Holistic Trajectory Calibration](https://arxiv.org/abs/2601.15778) finds trajectory-level features outperform the model's own confidence). The right role for both tools is therefore a hint that supplements deterministic triggers. LivePlan shows the winning shape: a rule-based monitor on drift, repetition and premature termination triggers the LLM advisor, giving up to +15.2% resolve (average +9.9%) at about $0.08 per instance ([arXiv 2608.06701](https://arxiv.org/abs/2608.06701), abstract-level). Anthropic also identifies two call moments that drive coding gains: after initial orientation, and before declaring completion on hard tasks. Your end-of-task reviewer covers the second; nothing covers the first.

A security-minded corollary comes from the routing literature: any escalation trigger driven by model-visible text is an attack surface, since router-hijacking strings can force the strong model ([Rerouting LLM Routers](https://arxiv.org/abs/2501.01818)). A tool result that talks the model into calling `request_escalation` repeatedly is a cost-escalation vector, so session-level caps matter.

## The reviewer works best on claim-versus-evidence checks, and evidence design beats model size

Your observation that the reviewer catches real over-claims matches the literature's best case: a claim with no supporting tool call is something even weak detectors find. A study of agent false-success found 35.6% of tau2-bench failures were false successes, and LLM judges reached at most **0.65 AUROC** because they anchor on confident language and on action-sequence volume, with reasoning models giving no improvement ([arXiv 2606.09863](https://arxiv.org/html/2606.09863)). The same study found that non-LLM detectors reached AUROC 0.83 to 0.95 at roughly 3,300x lower cost, and that environments with independent verification had about 3% false success versus 45-48% without. A mobile-agent judge benchmark found that agent reasoning text added at most 0.3 points while the model backbone was the main driver ([2608.11434](https://arxiv.org/html/2608.11434v1)). Together this implies a heavier reviewer helps, but the evidence it sees matters more, and deterministic checks (exit codes, test results, whether state changed at all) should run before any LLM review. The reviewer's weak performance on vague tasks fits the unsolved problem of recovering acceptance criteria; no source measured it, so the fix below is a design suggestion.

Two further risks apply. Self-preference bias is documented, as is a judge's tendency to favour its own outputs ([Panickssery et al.](https://arxiv.org/pdf/2404.13076)), but its magnitude for Claude-reviews-Claude agent traces was not found. And refinement against an LLM judge can inflate judge scores while true quality declines ([Pan et al.](https://arxiv.org/pdf/2407.04549), snippet-level), which is why the worker should receive checkable instructions ("run X and show the output") rather than opinions.

## Prioritised recommendations

1. **Treat empty or unparseable reviewer output as "unsure" with one retry, never pass or fail.** Log every occurrence. Judge malformed-output failure modes are recognised ([2603.22214](https://arxiv.org/pdf/2603.22214), snippet-level), and you observed one empty reply. Implementation: wrap the reviewer call, validate the verdict field, retry once with a shorter prompt, then record `unsure:error` and surface it to the user instead of silently passing.
2. **Add a pre-reviewer deterministic stage and skip rules.** Compute from the trail: whether any state-changing tool call occurred, last test or build exit code, and a map from claims such as "confirmed" or "tests pass" to tool calls. Skip review when nothing changed and the answer makes no verifiable claim (design reasoning; unmeasured). Re-review a fix round only if the working state changed since the last round.
3. **Rebuild the reviewer's evidence packet.** Include the task text, extracted claims, the verbatim supporting tool results per claim, explicit "[trail clipped here]" markers, and the worker's narration last or separately. Ask for a both-sides "true because / false because" step ([2609.10996](https://arxiv.org/html/2609.10996v1), calibration of a judge, not an agent). For vague tasks, have the reviewer first state the acceptance criteria it infers and return "unsure" when none are recoverable. No ablation of this ordering exists; test it on your logged sessions.
4. **Run a baseline experiment before tuning anything else.** Compare the ladder against (a) the stronger model at low effort and (b) the cheap model with a higher effort, on a fixed set of real tasks, measured live. Anthropic recommends this explicitly, and the coding effort curve is steep. If the baseline wins on cost-adjusted success, change the default tier to be task-type dependent. Replay of logged sessions will mispredict outcomes, so run the tasks live ([Replay Gap](https://arxiv.org/abs/2608.08239); [TwinRouterBench](https://arxiv.org/abs/2605.18859) offers a live track).
5. **Make handoffs cache- and context-aware.** Add a switching-cost term: estimate re-ingest cost as context tokens times the new model's write price, and gate non-urgent escalations and all step-downs on it. Add a minimum dwell per rung and a cap on switches per task. Prefer a consult over a switch for a single hard step. Test a compacted or trimmed handoff (task, repo state, a summary of failed attempts) against full-history escalation, and keep full history on step-down. Measure both direction and cost.
6. **Allow skip-level escalation on strong signals.** Refusal, failed independent review and breaker-adjacent loops should be able to jump two rungs; mild signals stay one rung. This is untested, so log counterfactuals and compare.
7. **Extend the detectors with progress-based soft signals.** Normalise signatures by hashing tool name plus normalised arguments, excluding free-text description fields, and compare observation hashes after stripping timestamps, durations and PIDs. Add windowed counters of about 10 actions for read-only streaks without a write or validation command, edit-then-revert on one file, and tests-failing-count not improving. Feed them into a cumulative risk score that triggers escalation, not abort. Add a one-time nudge naming the repeated action and the identical result before the third strike, as OpenHands does for errors.
8. **Define breaker state and half-open behaviour.** Persist breaker counters and trip time by session id in a file outside the reloadable module. Make the next user prompt a half-open probe rather than a full reset: allow limited tool use, re-trip faster on probe failure, and give the probe a budget so it cannot hang (the stuck-half-open bug class). Never leave the user without a "continue anyway" path.
9. **Demote request_escalation and consult_oracle to hints, and steer them with prompt text.** Weight low stated confidence as informative and ignore high confidence. Add system-prompt guidance for the two known high-value consult moments (after orientation, before completion), and log the consult rate per task type. Evaluate whether the native advisor tool (`advisor_20260301`, Anthropic API only, experimental) can replace `consult_oracle`, with `max_uses` as the cost cap; check compatibility with your harness first.
10. **Add fail-safe and abuse controls.** If a signal source fails, default to the higher rung or at least make the failure visible, as the GPT-5 router outage showed ([TechCrunch](https://techcrunch.com/2025/08/08/sam-altman-addresses-bumpy-gpt-5-rollout-bringing-4o-back-and-the-chart-crime/)). Cap total escalations and oracle calls per session. Enforce hard token and step caps per rung; use USD only as advisory, since Anthropic labels cost totals as client-side estimates.
11. **Log outcomes against an external check.** In-loop metrics can stay healthy while delivered quality falls: a 2026 verifier study saw flat roughly 3% in-loop error while delivered error reached 32% ([2609.01345](https://arxiv.org/abs/2609.01345), abstract-level). Record test outcomes, reviewer verdicts and user corrections next to every escalation, then compute your own reliability curves for each signal, including self-reported confidence.

## Evidence quality: what to trust and what to re-check

Strong foundations (peer-reviewed or primary documentation): Huang et al. and Kamoi et al. on self-correction, CRITIC, Panickssery on self-preference, FrugalGPT/RouteLLM/AutoMix on cascades, and the source code of OpenHands, Roo, Aider and CrewAI loop and iteration guards, read directly from main branches (so thresholds reflect current code, not a pinned release). Vendor documentation on caching and the advisor tool is primary but vendor-reported, and its benchmark numbers (including the model names and versions on the "Optimizing for cost and intelligence" page) came through a summarising fetch and should be re-checked against the live page before quoting.

Read at abstract level only, with effect sizes unconfirmed: The Handoff Tax (2608.24358), TACIT-Switch (2608.27911), AgentRouter (2609.22951, a workshop paper with self-reported 72% savings), MTRouter, SWE-Router (2607.00053), LivePlan (2608.06701), "Is Escalation Worth It?" (2605.06350), TwinRouterBench, ORACLE (2607.22465) and Cheap Verifiers, Large Blind Spots (2609.01345). Fetched by a summarising model, so figures are only as good as the summary: the false-success study (2606.09863), MobileJudgeBench (2608.11434), the LLM-as-a-Verifier paper (2607.05391) and the confidence calibration study (2609.10996). Snippet-level or unverified: the MAST percentages (via a search summary), the SWE-smith repeat statistics, Cline's 3/5 identical-call thresholds, Amp oracle details (official page failed to load; community gist and secondary summaries), Pan et al. on reward hacking, and the Springer reward-hacking survey. Low confidence, do not cite without checking: arXiv 2609.00038, 2609.20812 and 2609.02246 (quantitative claims). Practitioner and vendor blogs (Sonar, akitaonrails, Hannecke, GitHub issues) are anecdotal and are used here only as illustration.

Coverage gaps worth knowing. No source tests Claude-family Haiku/Sonnet/Opus rung ladders. None measures reviewer accuracy on Claude Code style sessions with clipped trails, round-two versus round-one review gains, oscillation rates in worker-reviewer loops, or the right value of N for step-down. There is no published precision or recall for any stuck detector. Not researched: Devin, Windsurf, LangGraph's numeric default, Claude Code hook-level protections (including Stop-hook re-entry guards), and the cross-agent table in "Inside the Scaffold" (2604.03515), which probably holds a useful systematic comparison.

## Conclusion

The ladder's architecture is closer to the research frontier than its rough edges suggest: behavioural triggers, consult-plus-switch, a bounded independent reviewer and a three-strike breaker are all independently converging patterns. The differences are in the margins that the literature has begun to quantify. Switching is an intervention with a measurable handoff penalty and a cache bill, not a free upgrade. Detectors tuned for exact repetition miss the stalls that dominate coding failures. A reviewer is only as good as the evidence packet it is shown.

The most useful single next step is evaluative rather than architectural. Because nobody has published tuned thresholds, Claude-specific calibration or a live cheap-first versus strong-model-at-low-effort comparison, the ladder's own logs, correlated with test outcomes and run live, are likely to be the best evidence available. Instrument first (recommendation 11), run the baseline comparison (recommendation 4), and let those numbers set N, the dwell time and the starting tier.
